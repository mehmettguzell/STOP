# Phase 1 Data Model: CI/CD Pipeline Quality & Performance

This feature has no application database schema. The entities below (carried over from
spec.md's Key Entities) are pipeline-level concepts, each backed by a concrete artifact rather
than a database table.

## Service

**Represents**: One of the five independently deployable backend components.

**Identity**: Directory name / ECR repository suffix — `identity-service`, `match-service`,
`communication-service`, `notification-service`, `api-gateway`.

**Attributes**:
- Source directory (`<service>/`) — what `dorny/paths-filter` watches to decide if this Service
  is "affected" by a given push.
- Own test suite (`<service>/src/test/java/...`), including new Testcontainers `*IT.java` classes.
- Own Dockerfile → own ECR repository (`stop/<service>`).

**Relationships**: A Pipeline Run's job matrix is a subset of these five Services.

## Pipeline Run

**Represents**: A single GitHub Actions execution triggered by a push or pull request.

**Identity**: GitHub Actions run ID + triggering commit SHA.

**Attributes**:
- Trigger type: `pull_request` (test + build only, per FR-012) or `push` to `main` (test + build
  + deploy).
- Affected-services matrix (output of the `changes` job).
- Per-service stage outcomes (test pass/fail, build pass/fail, deploy pass/fail).

**Relationships**: Produces zero or more Deployed Versions (one per affected Service, on a
`push`-triggered run only).

## Deployed Version

**Represents**: An immutable, traceable build of one Service — either currently running in
production or the most recent known-healthy version (the rollback target).

**Identity**: `<ECR_REGISTRY>/stop/<service>:<git-sha>`.

**Attributes**:
- Git SHA tag (immutable, always pushed).
- `latest` tag pointer (mutable, only advanced after the post-build healthcheck passes).
- Currently-deployed marker: the value in `.last-deployed-tag` on the EC2 host, one line per
  service or a single shared value if all services deploy in lockstep (see tasks.md for the
  chosen granularity).

**State transitions**: `built` → `healthcheck-passed` (eligible for `latest`) →
`deployed` → either stays `deployed` (next run's rollback target) or `rolled-back-from` (if the
next deploy of this Service fails its post-deploy check).

**Relationships**: A Deployed Version belongs to exactly one Service and is produced by exactly
one Pipeline Run.

## Release

**Represents**: An automatically computed semantic version + changelog covering everything
merged since the previous Release.

**Identity**: Git tag (e.g. `v1.4.0`) + GitHub Release.

**Attributes**:
- Computed version bump (patch/minor/major), derived from conventional-commit prefixes since the
  last Release.
- Changelog body, auto-generated by `release-please`.

**Relationships**: Independent of individual Deployed Versions — a Release describes a point in
overall project history, not a single Service's build. Multiple Deployed Versions (across
different Services, across different Pipeline Runs) can fall within one Release's commit range.
